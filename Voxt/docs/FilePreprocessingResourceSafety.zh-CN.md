# 文件任务：流式预处理与资源安全

状态：第一阶段代码与回归测试已补充；当前环境为 Linux，尚未运行 macOS 编译、XCTest 或真机性能验收。本文不代表内存峰值、处理时长或识别准确率已达标。

## 范围与流程

沿用会议的 ASR、说话人分析与详情摘要配置，不增加有损压缩、降噪、人声提取或静音拼接。标准化目标仍为 16 kHz、单声道、16-bit PCM WAV；多音轨仍沿用原实现选择第一条音轨。本阶段不宣称提高识别准确率。

```text
上传/拖入 → 立即显示排队记录
         → 等待预处理（保留原始授权 URL，不读取全文件）
         → 正在准备音频：流式解码、转换、增量写 .partial
         → 校验 WAV，原子重命名为 .prepared.wav
         → 等待分析 → 转录 → 说话人分析 → 保存历史
```

队列内预处理与文件分析互斥，一次只执行一个文件的重工作，不通过同时处理下一个文件来隐藏预处理成本。原始视频不再先完整复制到应用暂存目录；用户原文件不修改。

## 已实现的约束

- 新队列最多保留 64 条任务记录，达到上限时明确提示清理已结束任务；待处理项只持有任务信息、URL 和授权，不持有解码后的音频。
- **保留原有 4 GiB 源文件准入上限**，不在缺少大容器压测证据时直接放开。标准化音频及遗留暂存文件使用 8 GiB 队列配额，孤立完整缓存也计入磁盘占用。
- 元数据预检与实际输出双重限制：最长 12 小时；累计解码样本和 PCM 输出字节都受上限约束，不能用伪造的短时长绕过输出预算。
- `AVAssetReader` 按需取一个 buffer，同步完成转换与写盘后才读取下一个；不创建无界生产者/消费者队列，不把整段媒体或 PCM 加载到内存。
- 拒绝超过 4 MiB 的已交付解码 buffer；转换工作块最多 64 KiB Float 数据和 32 KiB PCM 数据。拒绝不完整 Float 数据和 NaN/Infinity，避免数值转换陷阱。分析窗口读取也强制最多 60 秒，并拒绝越界或不完整窗口，不能通过错误 descriptor 意外读取整场音频。
- 每个解码 buffer 使用独立 `autoreleasepool`，历史归档副本按最多 1 MiB 块读写并逐块释放临时对象。
- 队列预处理与归档复制运行在 utility 后台任务中。当前文件路径在内存 critical、温度 serious/critical 时在检查点等待，普通 warning 不再一刀切阻塞有界文件工作；录音开始时队列预处理也在检查点等待。utility 优先级本身不是 CPU 使用率上限。
- 写入前检查预计空间；转换中按时间/处理量定期检查，归档复制逐块检查。至少保留 512 MiB 空间，并为接下来的有界写入留余量；磁盘不足明确失败，不继续向分析队列交付结果。
- `.partial` 使用 `0600` 权限；结束后验证完整 PCM 头、格式、文件长度和样本上限，再在同目录重命名。失败/取消要等解码任务退出、句柄关闭后清理；取消中的任务不属于可清理的已结束任务。
- 处理中检查源文件大小、修改时间和文件身份是否改变；改变时拒绝发布结果。这不是跨导入内容去重，也不是完整文件哈希校验。

## 缓存、历史与恢复

`MeetingFileTask.preparedAudioVersion` 标记标准化缓存版本，队列持久化版本升级为 2，并兼容读取版本 1 的任务。旧的原文件暂存任务在轮到执行时才标准化；旧源暂存文件保留至任务清理，避免迁移中的元数据写入失败造成唯一源文件丢失。

- 重试分析不重新解码原文件，直接校验并复用标准化缓存。
- 崩溃发生在缓存重命名之后、任务元数据更新之前时，可根据确定的缓存路径校验并恢复。
- 启动清理已知任务及应用命名规则下遗留的 `.partial` 文件；损坏的缓存不会进入 ASR。
- 尚未完成预处理的用户授权 URL 不跨进程持久化；退出后若没有完整缓存或旧暂存源，需要重新添加原文件。这里不宣称任意解码位置续跑。
- 历史存储会移动音频文件。当前分析直接只读标准化队列缓存；全部分析成功且任务开始时开启历史音频存储，才在保存阶段有界复制独立归档。分析失败/取消或未开启存储不做这次复制。保存历史、回滚历史、清理任务不会消费另一方拥有的音频，成功归档仍有复制 I/O，不是“零复制”。
- 本阶段只复用预处理成果，**不包含 ASR/说话人阶段的片段级续跑**；分析失败后仍会重新进行这些阶段。

空间收益不能一概而论：标准化 PCM 每小时约 115 MB，视频通常明显精简，但低码率 MP3/AAC 可能变大；成功保存时缓存与独立归档副本还可能同时存在。保留缓存到用户清理任务换取重试能力，由队列配额和磁盘余量限制控制空间，不能宣称所有输入的磁盘峰值都下降。

## 资源安全边界

这些约束限制的是应用侧工作队列、显式缓冲及磁盘输出。`AVAssetReader` 必须先返回 buffer，应用才能检查其大小；容器解析、系统解码器内部缓存及同步解码调用仍由 AVFoundation 管理。不能据此宣称整个进程 RSS 小于 4 MiB、取消有硬实时保证，或任意异常媒体都绝不会造成 OOM。

若真机发现特定容器/编码器的内部峰值不可控，先限制该输入路径，再评估独立进程解码与强制终止；不能只增大 buffer 上限放行。预处理完成日志记录样本数、输出字节、最大已接受 decoder buffer 和墙钟耗时，不记录源路径或音频内容；RSS/CPU/GPU/能耗需另行采样。

## 长文件失败诊断

一次用户提供的约两小时视频测试日志显示：`samples=116040324`、`outputBytes=232080692`、`peakDecoderBufferBytes=17836`、`elapsed=15.62977475 seconds`。这证明该次标准化音频（约 7252.52 秒）已完成生成，后续还出现了 Qwen3 ASR 模型加载及转录过滤日志；不能把稍后任务失败直接归因于预处理。17.42 KiB 是最大已接受解码 buffer，不是进程内存峰值。

旧版队列只将失败原因保存到任务元数据/通知，未记录失败日志，因此仅凭这份控制台输出无法定位最终错误。特别需要核实推理准入的温度/内存拒绝：当前 `.fileASR` 在安全限制下会抛错，严格转录将其向上传递为文件任务失败，而不是自动等待恢复。这是一条已确认的代码路径，不是该次事故已确认的根因；本次诊断补丁不修改准入保护或自动重试策略。

新增诊断包括：

- 任务预处理开始/就绪、分析开始、阶段变化、按进度阈值节流的心跳、失败和完成日志，带 task ID、阶段、墙钟耗时、已处理音频时长、总音频时长及温度状态。
- 严格 MLX ASR 失败记录当前音频块的起止秒数、模型、工作类型和异常类别/代码，仍原样抛出错误，不吞错或返回部分成功。
- 推理准入拒绝明确标记 `thermal-pressure`、`memory-pressure` 或 `inference-queue-full`。
- 任务行显示具体处理阶段；失败提示包含保留的失败阶段和原始用户可见错误。
- 诊断错误摘要不展开任意错误描述、请求载荷或 userInfo；不记录文件名、音频内容或转录文本。

对已有失败任务，在清理/重试前读取 `~/Library/Application Support/Voxt/meeting-file-tasks/tasks.json` 的 `progressStage`、`errorMessage`、`processedMediaDurationSeconds`、`startedAt`、`completedAt`（沙盒运行时可能在容器下）。`processedMediaDurationSeconds` 是进度估计，不是精确失败块位置；新 ASR 错误日志中的块范围用于精确定位。分享时无需发送源路径、文件名或媒体内容。预处理成功、后续 ASR 失败仍应分别诊断。

### 日志策略

常规日志只保留任务开始、阶段切换、资源等待开始、失败和完成。默认不再输出解码/复制进度、队列心跳、ASR 分块、说话人 feed、许可进出或缓存回收快照。

需要复现时才设置 `VOXT_FILE_TASK_TRACE=1` 并重启；Debug 和 Release 默认都关闭。详细事件仍由 `MeetingFileTrace` 输出，前缀为 `[FileTaskTrace]`，仅包含状态、数量、随机 ID 和错误类别，不包含媒体内容或文件路径。任务 ID 由独立的 `MeetingFileTaskContext` 传递，不依赖日志开关。

沿用现有滚动日志存储（单文件约 2 MiB，保留 5 个归档），不另建无界日志文件：

```text
~/Library/Application Support/Voxt/Logs/current.log
~/Library/Application Support/Voxt/Logs/archive/
```

沙盒构建可能在应用容器对应目录中。复现后尽快通过应用日志导出功能导出，或一起收集 current.log 与 archive；长任务的早期日志可能已轮转。Xcode 控制台可筛选 `FileTaskTrace`，再按 task ID 查完整链路。最后一个 `asr-chunk-started` / `speaker-window-started` 与对应完成/错误事件可区分排队、推理、失败及清理，不必猜测总进度。

新增/扩展测试：

- `MeetingImportedAudioFileTests`：目标格式、窗口读取、原文件保持不变、完整产物发布、取消清理、输入大小/时长/输出/磁盘限制、缓存格式校验、实际解码样本与 buffer 上限、归档副本独立性。
- `MeetingFileTaskQueueTests`：预处理与分析不重叠、FIFO/优先级、取消后不启动分析、缓存重试、旧队列迁移、重启恢复、损坏缓存拦截、排队数量上限。
- 保留 `MeetingImportedFileAnalyzerTests` 的取消与资源所有权回归。

macOS 运行：

```bash
xcodebuild test -project Voxt.xcodeproj -scheme Voxt \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO \
  -only-testing:VoxtTests/MeetingImportedAudioFileTests \
  -only-testing:VoxtTests/MeetingFileTaskQueueTests \
  -only-testing:VoxtTests/MeetingImportedFileAnalyzerTests
```

合入前的真机门禁：

1. 同设备、同输入，对比 10/60/180 分钟音频与接近准入上限的大视频，分别记录预处理及整条链路的耗时、RSS/physical footprint、CPU/GPU、swap、温度、临时磁盘峰值。
2. 覆盖高采样率、多声道、无音轨、多音轨、损坏/截断媒体、密集批量导入、低磁盘空间、预处理中修改或删除源文件。
3. 转换、重命名、分析、保存历史各边界执行取消/退出/重启；确认无半成品进入模型、无历史音频误删、无取消后新任务被旧回调污染。
4. 内存/温度压力、实时录音开始后，确认检查点能停止继续读取，恢复后能继续；观察系统解码器暂停期间的内存行为。
5. 预处理应用侧缓冲不随媒体总时长线性增长；没有持续内存爬升、明显主线程卡顿或磁盘越界。具体进程内存与 CPU 准入预算须由目标设备实测制定。
6. 转录准确率、说话人归属、时间轴及历史回放不得因为本阶段流程改动退化；不要用“文件更小”替代质量验证。
