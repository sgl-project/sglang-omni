# Nemotron Transcribe: serving the native MTP layer as a speculative draft

`nvidia/Nemotron-3.5-Transcribe-30B-A4B` ships one multi-token-prediction (MTP) layer under `llm.mtp.*` next to its NemotronH decoder. The model card uses it as an EAGLE-style draft: the layer takes the decoder's last hidden state and the embedding of the token just produced, proposes the next token, and is replayed on its own output to propose several more. This document describes how sglang-omni serves that draft, what had to change, and what was measured.

## The model and the integration

The checkpoint has three parts. A Parallel Expert Encoder turns audio into embeddings that stand in for the audio placeholder tokens of the prompt. The NemotronH decoder, a hybrid of Mamba2, attention and MoE layers with about 4B active parameters, generates the transcript autoregressively from that prompt. A CTC timestamp head aligns the transcript to the audio; this integration does not serve it. Only the decoder is autoregressive, and it is the part the draft accelerates.

Before this change `checkpoint_contract.py` skipped every `llm.mtp.*` tensor, and the integration served the decoder without a draft.

## What SGLang already provides

Upstream SGLang carries everything that runs the draft. `NemotronHForCausalLMMTP` is the draft model: one attention block and one MoE block with the `enorm`, `hnorm` and `eh_proj` start projections, driven by `EAGLEWorkerV2`, which chains the layer for `speculative_num_steps` steps and verifies `speculative_num_draft_tokens` tokens per target forward. The draft is selected with `--speculative-algorithm NEXTN` (an alias of EAGLE) and a draft path equal to the target path; `ModelConfig(is_draft_model=True)` rewrites a `NemotronHForCausalLM` architecture to `NemotronHForCausalLMMTP`.

Mamba state rollback is handled without model code. When `speculative_num_draft_tokens` is set, the Mamba pool allocates per-draft-token snapshots of the SSM state and the convolution window; the Mamba2 verify path writes one snapshot per draft token instead of advancing the persistent state, and after verification the worker scatters the snapshot of the last accepted token back into the request's slot. NemotronH already routes its Mamba layers through that path.

## What this change adds

**Loading the draft from the NeMo checkpoint.** The upstream draft class expects Hugging Face names. `classify_checkpoint_name(name, is_mtp_draft=True)` keeps only `llm.mtp.*`, renames it to `mtp.*` and routes the MoE tensors through the same fused-expert split and transpose the decoder uses (`experts.gate_and_up_projs` and `experts.down_projs` are stored as one `[E, in, out]` tensor per layer). `NemotronTranscribeMTPDraft` subclasses `NemotronHForCausalLMMTP` and loads through that classification; the parent then rewrites `mtp.layers.` to `model.layers.`. The class is registered under the name `NemotronHForCausalLMMTP` because the architecture rewrite is keyed on that string. Embeddings and `lm_head` are not loaded by the draft; the worker shares the target's through `get_embed_and_head` and `set_lm_head_from_target`, which the `NemotronTranscribeForConditionalGeneration` wrapper now delegates to the decoder.

**Handing the draft the prompt embeddings.** After the target's prefill, the EAGLE worker runs the draft once over the whole prompt to build its KV cache, and `NemotronHMultiTokenPredictor.forward` asserts that it receives the prompt embeddings (`forward_batch.mm_input_embeds`) whenever the batch has multimodal inputs. The decoder composed those embeddings inside its own forward through `general_mm_embed_routine` and never published them. `NemotronTranscribeModelRunner.before_prefill` now composes them with `prepare_mm_inputs` and attaches them as the omni prefill sidecar on the batch the runner retains; the runner's existing retention path hands them to the speculative target worker, which places them on the logits output for the draft. The decoder forward takes the composed tensor as `input_embeds` and only composes it itself when none is given. Two details made this necessary: the upstream eager runner forwards a `replace()` copy of the `ForwardBatch`, so a sidecar attached inside `model.forward` is invisible to the runner, and `prepare_mm_inputs` sets `forward_batch.mm_inputs = None` once it has consumed the items, so any check for audio has to run before it.

**Engine wiring.** `NemotronTranscribeEngineBuilder.adjust_overrides` accepts `speculative_algorithm` EAGLE or NEXTN, points `speculative_draft_model_path` at the checkpoint shim directory (the shim carries the NemotronH config the draft's `ModelConfig` can parse; the original `config.json` is NeMo format), fills the default chain of 3 steps, top-k 1 and 4 draft tokens, and disables mixed chunking. `infra_kwargs` opts the stage into speculative decoding so the bootstrap builds the upstream EAGLE worker around the omni target worker. `make_model_runner` returns the Nemotron runner. The result adapter forwards the scheduler's `spec_tokens_details`, so a request sent with `return_spec_tokens_details=true` reports `spec_accept_length`, the proposed and accepted draft counts and the per-verify histogram.

**Request events.** The audio encoder, which runs inside the prefill forward when the pre-LM encoder is off, emits `encoder_start` and `encoder_end` request events, so a request profile can report the encoder's share separately from the decoder's.

**Architecture alias.** The Hugging Face release renamed its architecture to `Nemotron3_5TranscribeForConditionalGeneration`; the pipeline config now accepts that name as an alias. Without it the current checkpoint does not load at all.

## Verification

The draft was first measured offline, independent of the serving stack: `benchmarks/profiling/nemotron_transcribe_mtp/mtp_acceptance.py` rebuilds the MTP layer in PyTorch from the checkpoint tensors, chains it to depth 8 and counts, from every decode position of the target's greedy transcript, how many consecutive drafts equal the target's greedy tokens. Because verification is greedy, this is exactly the acceptance a served run sees. On seed-tts-eval-50 the conditional acceptance per depth stays between 0.99 and 0.97 through depth 8, giving acceptance lengths of 3.9 at three steps and 7.4 at eight; on the first 300 utterances of LibriSpeech test-clean the figures are 3.8 and 7.3.

Served on two L40S with the decoder tensor-parallel (the plumbing for that lives on the profiling branch), the same workload reports `spec_accept_length` 3.8 to 4.0 with the default chain and 7.0 to 7.5 with seven steps, matching the offline numbers, and corpus WER 0.0060 with and without the draft, with transcripts identical to the baseline's. At concurrency 1 the decoder's decode phase fell from 131.7 ms to 58.5 ms per request while prefill grew by 5 ms for the draft's extend over the prompt; RTFx went from 21.5 to 30.6 at concurrency 1 and from 48.9 to 98.2 at concurrency 8. Those L40S figures carry a PCIe all-reduce cost per layer and 864 GB/s of memory bandwidth, so the single-GPU H200 sweep in `run_mtp_sweep_h200.sbatch` is the reference measurement.

## Limits and follow-ups

The draft reads the whole 67 GB checkpoint a second time because the upstream loader streams every tensor through `load_weights`; a loader that reads only `llm.mtp.*` would cut startup. Only greedy decoding has been measured; at a sampling temperature the acceptance becomes probabilistic. A single 80 GB H100 does not hold the bf16 decoder, the draft and a KV pool together, so the draft needs an H200 or a tensor-parallel pair of smaller GPUs. `NemotronTranscribeModelRunner.before_prefill` has no unit test yet.
