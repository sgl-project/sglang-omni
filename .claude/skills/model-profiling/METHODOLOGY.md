# Model Runtime Profiling Methodology

## 0. Preface

This is a pure methodology document — it only describes **how to investigate** (what to check first, which tools to use, which pitfalls to avoid, how to tell "a real issue" from "noise"). It intentionally contains no model-specific measurements or conclusions. For a concrete case study (e.g. the Whisper numbers), see the model-specific investigation docs — do not add experiment data back into this file.

This file is the **canonical** version of the methodology. Any copy elsewhere (e.g. in the tracking issue's body) is a historical snapshot — when they disagree, this file wins.

**How to use this**: when you pick up a profiling task for a model, do Layer 1 first, then branch per §2's routing rule — the layers are ordered by cost-effectiveness, not as a fixed 1→5 sequence — and structure your report to match the checklist in §3. You don't need to find a problem at every layer — a negative result ("the current default is already fine, no change needed") is just as valid an outcome as a positive one, as long as the reasoning is written down clearly.

## 1. Environment and Pre-Flight Checklist

Do these before starting, or the data you collect later may be untrustworthy as a whole:

- [ ] **GPU selection: check both `utilization.gpu` and `memory.used`, never memory alone.** Shared hosts can exhibit a sustained contention pattern where memory looks clean but compute is pegged by another tenant — checking free memory alone can silently pick an unusable GPU. Check with:

  ```bash
  nvidia-smi --query-gpu=index,utilization.gpu,memory.used,memory.total --format=csv
  ```

  Spot-check this both before and during the run, since occupancy on a shared host can change at any time (there's also a "transient" flavor of contention — memory spiking to full and clearing again, triggering automatic KV-cache shrinkage — which is a different risk from the sustained kind and needs to be guarded against separately).
- [ ] **Record the baseline environment**: the pinned framework version (`pip show <package>` or the pin in `pyproject.toml` — and confirm the local editable install's actual checked-out commit matches that pin; the two can silently drift apart), GPU model, model checkpoint, dataset version/commit. After any core dependency upgrade, prior conclusions need to be re-verified before you can trust they still hold — always state which version you tested against in the report. **Don't check only the serving framework's own package.** On a shared host, other pinned core dependencies (e.g. `transformers`/`tokenizers`) can drift from the `pyproject.toml` pin just as silently (for instance, dragged along by an unrelated change to the shared environment from another project/tenant on the same box) — and the fallout from that drift isn't limited to "numbers become incomparable"; it can be a **hard startup failure**. One instance observed in this repo: serving code assumed a model-config sub-field had already been converted to an object and set an attribute on it directly, which only holds when the installed dependency version is in the expected range; with a drifted version the sub-field was still a raw dict, and the attribute-set raised `AttributeError`. Before profiling, cross-check every pinned core dependency (not just the serving framework), and when a server fails to start, suspect "is my local environment newer/older than the pin" before suspecting a real code bug — especially when the exact same version combination is already known to work in another profiling record. **Prefer a fix that doesn't affect other tenants on the shared host.** Rather than changing the shared host's global environment (which can affect other people/processes currently using the same machine), prefer an isolated override: `pip install <pkg>==<pinned-version> --target=<scratch-dir> --no-deps`, then prepend that directory to `PYTHONPATH` for only your own server process. Delete the scratch directory once you're done — it leaves no trace on the shared environment.
- [ ] **Pin the model checkpoint revision, not just the framework versions — HF `refs/main` can move mid-investigation.** Launching a server with a bare HF repo id resolves `refs/main` at boot time and will silently download whatever the upstream pushed most recently; verified in this repo: an upstream push that landed *during* an investigation changed the checkpoint's weight layout and produced a hard boot failure (`checkpoint weight <name> has no matching model parameter`) on a model that had booted fine from the same repo id before. When a previously-working launch suddenly fails in weight loading, check the HF cache first: multiple snapshot directories under `~/.cache/huggingface/hub/models--*/snapshots/` with different download timestamps, plus `refs/main` pointing at the newest, is the signature — diff the safetensors headers (key names/counts) across snapshots to confirm, rather than assuming the serving code regressed. To pin without touching the shared environment: if the serve CLI has no `--revision` flag, pass the resolved snapshot directory as `--model-path` and keep the public repo id via `--model-name` so benchmark clients' `model=` field still matches. Record the snapshot SHA in the report; also check whether the repo/CI pins a revision at all — if not, flag it, since the next cold-cache boot will hit the same breakage.
- [ ] **A benchmark replaying the same inputs across repeats can silently measure a cache-hit regime.** Serving code may cache expensive per-input stage outputs keyed by input content (e.g. a pre-LM encoder embedding cache) — with a fixed eval set, every repeat after the first hits the cache and skips that stage entirely (GPU encoder work included). Three tell-tale symptoms observed together in this repo: (a) a large first-pass-vs-steady-state throughput jump beyond what lazy-init explains; (b) a dedicated stage worker thread sampling as 100% idle under full load (sanity-check: at the observed request rate, even ~1ms of per-request work would show clearly nonzero occupancy — a flat zero means the stage isn't running at all, not that it's fast); (c) GPU busy ratio lower than the model's architecture would suggest. Before generalizing any steady-state number to production traffic, check the request path for content-keyed stage caches, and state explicitly which regime (cache-hit vs unseen-input) the numbers describe; measuring the unseen-input regime needs per-repeat-unique inputs or the cache disabled.
- [ ] **Confirm the process tree is clean**: check `nvidia-smi` on the target GPU before starting a server, looking for orphaned processes. `pkill -f <launch command string>` matches on cmdline and will **not** kill orphaned compile subprocesses (their cmdline is just an interpreter invocation, containing none of the launch command string) — these have been observed to survive for 80+ minutes unkilled. Kill by process group, or by PID individually — don't trust `pkill -f` alone.
- [ ] **On a shared host, isolate CPU cores**: when multiple GPU jobs share one host without CPU isolation, results for the same config drift between runs — this is CPU contention, not GPU contention, but the symptom (numbers drifting, repeats not converging) is easy to misattribute to the GPU side. This repo already has ready-to-use CPU-pinning infrastructure — don't reinvent it: `.github/scripts/pin_to_ci_cpuset.sh` (used by CI), `_apply_omni_ci_cpuset`/`_parse_cpuset` in `tests/test_model/conftest.py` (process-level pinning via `os.sched_setaffinity`), and `examples/mps_dp/{launch,autodp}.sh` (`numactl --cpunodebind/--membind/-C` for NUMA+CPU binding). Reuse these scripts' pinning approach for the benchmark and server processes, assigning disjoint core ranges, and record which cores were bound in the report.
- [ ] **The first substantial load right after a server starts can be measurably slower than steady state, even after the eval script's own configured `--warmup N` has already run**: observed across multiple models — running the exact same batch of sample ids as (a) part of the first large load right after server startup versus (b) a standalone repeat after the server has already processed several batches of load can show clearly worse latency/RTF-style numbers for (a), and this gap is highly reproducible across repeats (not noise). The eval script's own `--warmup 1`-style pass is not always enough to fully absorb this — the warmup's scale (one pass vs. the real load of dozens-to-hundreds of requests) may not be enough to trigger certain lazy-loading/cache-warming code paths. **What to do**: before trusting any number as "steady state" for trend analysis or an A/B comparison, make sure at least one real, substantially-sized load has already run against that server instance (beyond just the script's own warmup pass) — and ideally re-run the same sample-id batch once more to confirm the numbers have already converged, rather than trusting whatever the very first run after server startup produced.
- [ ] **A clean server boot log (e.g. `Uvicorn running` printed with no errors) does not guarantee the first real request will succeed**: some optional dependencies are only lazily imported on a request-processing code path (e.g. a branch that only handles a specific language/format), and the import only executes — and only fails, if the dependency is missing — once a request that actually exercises that branch arrives; the same applies beyond imports to any under-exercised branch whose bug only surfaces once real traffic reaches it, not at boot time. **What to do**: after the server reports it's ready, send one real request that exercises the code path you care about, and confirm it returns a correct end-to-end result, before trusting any subsequent load-test/profiling data — don't treat "no ERROR in the boot log" alone as proof the environment is ready.

## 2. Core Investigation Methodology (Layered, Ordered by Cost-Effectiveness)

Do Layer 1 first to establish the big-picture direction (is the bottleneck GPU compute or CPU/orchestration), then decide which layer to drill into next — don't jump straight to an A/B on some specific knob.

### Layer 1: GPU Busy Ratio — Is the Bottleneck GPU Compute or CPU/Orchestration?

Four independently-usable measurement methods; their conclusions should corroborate each other (if they don't, it's usually the "CUDA-graph blind spot" described below, not the methods genuinely disagreeing):

1. **Kernel-timing method**: with the server running, use the native `/start_profile` → load-test → `/stop_profile` (`enable_torch=true`), export the chrome trace (`trace_pid*.trace.json.gz`), take the **union of the time intervals** of every entry with `cat=="kernel"` (not a naive sum — summing overlapping kernels across multiple streams double-counts; see "the correct way to compute busy ratio" below), and divide by the wall time of the kernel-activity window. If your profiler only exports the raw trace with no built-in summary table, you'll need a one-off script to parse it. **Known blind spot**: if the model's decode/prefill path relies heavily on CUDA graph replay (true of most of sglang-omni's decode path), the replay's execution time lands in CUPTI under the `GRAPH_TRACE` activity kind, not `KERNEL` — taking the union over only `cat=="kernel"` can significantly under-count the real busy ratio; you need to fold `GRAPH_TRACE` and other relevant kinds into the union too. **This blind spot also has a version-dependent variant, verified in this repo's own environment**: on torch 2.11+cu13.0, the trace confirmed has no `GRAPH_TRACE` category at all — consistent with reports from other environments. But the alternative detection idea ("graph replay kernel events carry a graph-id-style arg") did NOT hold on this version either — `cat=="kernel"` events here only carry occupancy/grid/block/stream fields, no graph-id marker. Instead, graph replay showed up as `cudaGraphLaunch` events under `cat=="cuda_runtime"`, not `kernel`. So don't hardcode either "look for `GRAPH_TRACE`" or "look for a graph-id kernel arg" — inspect what categories are actually present in this trace and whether `cuda_runtime` contains `cudaGraphLaunch`-style events before deciding how to detect graph replay; the trace's structure and fields are not consistent across torch/CUDA versions.
2. **nvidia-smi sampling method**: use your eval script's `--sample-util --util-gpu-ids <gpu>` flag to periodically read `nvidia-smi`'s `utilization.gpu` during the load test. Doesn't depend on a profiler, has lower overhead, and is well suited to long-running or high-concurrency scenarios. **Limitation one**: `utilization.gpu` is fundamentally just "was any kernel executing during this sampling tick" — it says nothing about how much of the SM array was actually occupied. A kernel that only uses a handful of SMs but runs continuously can still read near 100%, at which point this number can no longer tell you whether the GPU is actually saturated. **Limitation two**: short load-test windows can produce very few samples, or none at all — verified in this repo: the eval script's `UtilizationSampler` (`benchmarks/eval/asr_profiling.py`) waits an interval *before* taking each sample, and the default `--util-interval=1.0` means any repeat with wall time under ~1s gets **zero** samples, not just few (reproduced across 5 repeats with wall time 15–135ms, all landing `n_samples=0`). Lowering the interval doesn't fully fix this either — actual sampling cadence is floored by how long a single `nvidia-smi` invocation itself takes (observed 180–340ms per call). Separately, `utilization.gpu` reading exactly 0% during a genuine short idle gap is a correct instantaneous reading, not a bug — the risk is over-generalizing it to "the whole repeat did nothing." So report **the sample count and the raw values** alongside the mean; treat `n_samples=0` or a clearly low count (e.g. under 20) as directional at best, never as a conclusion; and if the workload itself is short, lengthen it or loop multiple repeats until you accumulate enough samples to average. **There is a subtler bias when `n_samples` is nonzero but still small**: those few samples are not "noisy but directionally-correct sparse estimates" — they tend to land systematically during the ramp-up/warmup phase (GPU utilization climbing from 0 toward steady state) rather than the steady state itself. Verified in this repo: the same config's short-window mean utilization can read at roughly a quarter of the true steady-state value, while lengthening the window (to hundreds of samples) reveals the full "0% → ramp → sustained plateau" curve, with the short window's handful of samples landing almost entirely inside the ramp segment. Whether a batch of samples has actually reached steady state isn't just a question of `n_samples` being large enough — also check whether the total load-test duration clearly exceeds the model's typical ramp-up time (run one long window first to trace the ramp curve and estimate how long it takes). **A related but easier-to-miss bias — the sampling window not being aligned with the load test's real active span**: if you're using a hand-written sampling loop (rather than the eval script's built-in `--sample-util`), and its start/stop times leave a large gap relative to when the load test itself actually starts/stops (e.g. starting the sampler tens of seconds early, or stopping it long after the load test already finished), the GPU may genuinely be idle during that gap (perhaps because the load-test script is still doing dataset download/staging), so the 0% readings are individually correct — but averaging them in drags the aggregate well below the load test's real active-period level, and it's easy to misread this as "this workload just has low utilization." This is a different root cause from "the whole window is too short and lands entirely in ramp-up" (one is the window being too short overall, the other is the window being long enough but with large idle gaps at either end that don't overlap the load test), but the symptom and the fix are similar: **tightly bracket the sampler's start/stop around the load-test invocation itself** (leave only ~0.5–1s of slack on either side) — don't let the sampler start much earlier or stop much later just for convenience.
3. **DCGM continuous-sampling method (more precise than nvidia-smi, lighter than nsys — good for long-running/production scenarios)**: if `dcgmi` is available in the environment (with `nv-hostengine` resident), you can sample SM Active / Tensor Active directly as profiling-field metrics, without wrapping the whole server launch in a profiler the way nsys requires:

   ```bash
   dcgmi dmon -e 1002,1004 -d <sampling interval ms> -i <gpu-index>
   ```

   `1002` is `DCGM_FI_PROF_SM_ACTIVE` (SM Active), `1004` is `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` (Tensor Active); cross-check the actual field ids with `dcgmi dmon -l`. This method doesn't require restarting/wrapping the server process, making it a good default for day-to-day/long-running scenarios where you want more precision than `utilization.gpu` without paying the one-off deep-dive overhead of nsys; reserve nsys GPU Metrics (method 4) for scenarios where you need to pin down a specific one-off issue with maximum precision. **If `dcgmi dmon` reads 0.000 for the entire run, don't immediately suspect a DCGM profiling-permission/instrumentation problem** — the far more common cause is the sampling-window-alignment issue described under method 2 above (the `dcgmi dmon` start/stop not overlapping the load test's real active span). How to rule this in/out: (a) cross-check the GPU index/UUID mapping between `nvidia-smi -L` and `dcgmi discovery -l` to make sure you're sampling the right card; (b) run an independent synthetic load known to occupy the GPU (e.g. a tight matmul loop) while `dcgmi dmon` is running, and confirm DCGM reports nonzero SM Active/Tensor Active for it — if it does, DCGM itself is working fine, and the all-zero reading is almost certainly a window-alignment artifact; go back and tightly bracket the sampler around the load test per method 2's guidance, rather than continuing to chase a DCGM permission/namespace explanation.
4. **nsys GPU Metrics method (one-off deep-dive scenarios — highest precision, but also the highest overhead/intrusiveness)**: sample the hardware counters directly for the SM/Tensor Core occupancy time series:

   ```bash
   nsys profile --trace=cuda,osrt,nvtx \
     --gpu-metrics-devices=cuda-visible \
     --gpu-metrics-set=<the metric set for this GPU architecture — check available values with `nsys profile --gpu-metrics-set=help`> \
     --gpu-metrics-frequency=100 \
     -o <out> -- <the full server launch command>
   ```

   **Critical pitfall**: sglang-omni's server process forks off the actual forward-executing subprocess, so attaching after the fact with `nsys profile -p <pid>` is unreliable for this kind of multi-process architecture — you must wrap the entire launch command in `nsys profile ... -- <command>` and run it under nsys from the start. Afterward, run `nsys export --type sqlite -o <out>.sqlite <out>.nsys-rep` and read the `GPU_METRICS` table from the exported sqlite, taking the time-series mean of the **SMs Active** and **Tensor Active** metrics. The metric-name-to-id mapping differs across GPUs/metric sets — don't hardcode ids; look up the mapping table in the sqlite first. This method has very low overhead (turning on GPU-metrics sampling adds almost no extra wall time), and pairs well with methods 1/2/3 for cross-validation, especially when you suspect method 1 hit the CUDA-graph blind spot, or that method 2/3's number is "inflated" (kernels are running, but the SM array isn't actually full).

**The correct way to compute busy ratio (avoiding two opposite-direction biases)**:
- **Overestimate**: naively summing the durations of multiple kernels/streams and dividing by wall time double-counts any time where kernels/streams overlap, inflating the ratio. The correct approach is to take the **union of the time intervals** across the relevant activity first, then divide that union's total duration by wall time.
- **Underestimate**: if the union is taken over the `KERNEL` activity kind alone, it misses other GPU-occupying activity kinds like CUDA graph replay (`GRAPH_TRACE`) and memory transfers (`MEMCPY`/`MEMSET`), which under-counts (potentially by a large margin for CUDA-graph-heavy models). The correct approach is to include every activity kind present in the trace that represents "the GPU is doing something" (at minimum `KERNEL` + `GRAPH_TRACE` + `MEMCPY` + `MEMSET`, adjusted to whatever kinds actually appear) before taking the union.
- **Deciding whether you need this stricter method**: check whether the model relies heavily on CUDA graph replay (if the server logs/config show graph-bucket configuration, it almost certainly does). If so, a busy ratio computed from a naive sum, or from a union over `KERNEL` alone, cannot be trusted — you need the multi-activity-kind union.

**Should the denominator also include the leading/trailing CPU queueing/wrap-up time? — No, that's intentional; it's a different question.** The kernel-activity window (from the first GPU activity to the last) already contains, internally, whatever gaps are caused by CPU scheduling/synchronization — those gaps are exactly why the busy ratio is below 100% in the first place, no extra handling needed. The real question is the time **outside** the window: there's CPU-only time between request queueing/construction and the first GPU activity, and between the last GPU activity and the response being returned, that isn't in this denominator. Whether to count that time depends on which question you're trying to answer — "how busy is the GPU within its active window" (Layer 1's question; the denominator should be the window's own wall time) versus "what fraction of end-to-end time does the GPU occupy" (a different question, already answered by Layer 3's "busy ratio drops as concurrency rises" investigation and by the request-level stage profiler). Don't merge the two into one metric just to save a measurement — doing so conflates two genuinely different root causes ("GPU compute itself is light" vs. "CPU queueing got heavier") into a single confusing number, making it harder, not easier, to diagnose.
**A companion pitfall**: if you do want to measure "CPU-only time outside the window," you must anchor it to the real start/end timestamps of GPU activity from the trace itself — you cannot use an application-level event marker (e.g. the request-level profiler's `scheduler_prefill_start` marker) as a stand-in for "when the first GPU activity started." Async operations like H2D memcpy can start on the GPU several milliseconds before such an application-level marker fires, so a "time outside the window" computed from application markers will read larger than it really is — align it against the real nsys/CUPTI trace timestamps instead.

**Known limitation (not currently feasible without new instrumentation)**: there is currently no way to extract "per-kernel execution time broken down by the batch size active at that moment" directly from existing chrome traces / CUPTI traces — the trace carries no batch-size context. Getting this granularity would require adding NVTX range push/pop around each forward call in the serving code, tagging the range with the batch size at that moment — a code change, not something a new parsing script can pull out of an existing trace.

Decision rule: if multiple methods measure a busy ratio well below 100%, the bottleneck is mainly CPU/orchestration, and the next step should be Layer 2 (py-spy) rather than obsessing over GPU kernel selection. Conversely, if the busy ratio is already high (near saturation), Layer 2–4 CPU-side investigation is likely low-yield, and you should pivot to kernel-level optimization instead. **Note**: this ratio's trend as a function of concurrency can flip entirely between workload shapes (e.g. short-clip vs. long-sequence) — always measure separately per workload shape for the same model; don't draw a conclusion from a single shape.

### Layer 2: CPU-Side py-spy Sampling — Finding the Real Source of Idle Overhead

**Sampling command template**:

```bash
py-spy record --format raw --idle --subprocesses --pid <engine-pid> \
  --duration 25 --rate 20 --output out.raw
```

**Critical pitfall (know this or you'll get results that look clean but are actually worthless)**: by default (without `--idle`), calls that block or release the GIL — CUDA calls, `queue.get()`, `zmq.poll()`, and the like — are skipped entirely during sampling, producing "Samples: 0, Errors: 0". This looks like a healthy run, but it means zero valid samples were actually captured. Use `py-spy dump --pid <pid>` first to look at a live thread stack and confirm the process really is busy but the default mode just can't see it, before deciding whether to add `--idle`.

- **Target process**: find the process actually doing scheduling + forward, not the top-level HTTP/API server process. In an architecture like sglang-omni's, this engine/scheduler process is typically a genuine fork-child of the top-level server process (observed with 100+ threads) — adding `--subprocesses` to the main process will pull in every child process, and you'll need to distinguish the scheduler/model-exec process from glue processes like `multiprocessing.resource_tracker` by cmdline (ignore the latter); if you already know the specific child PID, you can skip `--subprocesses` and attach directly to it instead.
- **Sampling rate**: if you don't yet know the target process's thread count or load intensity, start the first trial at a lower rate (e.g. `--rate 5`) and confirm the output shows no "fell behind"-style lag warning before considering raising it; discard any capture that does report lag — a sampler that can't keep up systematically drops high-frequency short calls, which is a biased loss, not just "fewer samples but still directionally right." In this repo's environment, an 8-second trial did not reproduce lag from `--rate 20 --subprocesses` against a 100+-thread engine process (and `--rate 5` attached directly to the child PID also showed no lag) — but that doesn't rule out lag appearing on longer sustained captures. Starting low and watching for the warning is more reliable than assuming any fixed rate is always safe.
- **There must be real load during sampling**: keep a benchmark script firing requests throughout, so the process is genuinely working, not idling right after startup.
- **Distinguish "one-time amortized cost" from "steady-state tax"**: a single sampling window isn't enough to draw a conclusion — do **at least 3 independent repeats** (same config, different time windows) and check whether the percentage converges to a stable number. If you suspect an overhead only shows up during startup/warmup, take an extra sample after the process has been running for a while and compare whether it has shrunk or disappeared.
- **How to read the flame graph / leaf frames**: group by leaf frame and compute each one's share of the **total sample count** (not "active frames," which is a much smaller denominator), while also judging qualitatively what that leaf frame's semantics actually are — is it a healthy idle state (genuinely nothing to do, waiting on a queue/socket), or some auxiliary infrastructure that shouldn't be sitting there spinning? Picking the wrong denominator (active frames instead of total samples) will directly inflate the percentage and can mislead prioritization. **Group by file:line, not bare function name**: verified in this repo that sglang-omni's own scheduler-thread entry function happens to also be named `_worker`, colliding with `concurrent.futures.thread`'s `_worker` — grouping by function name alone silently merges two semantically unrelated leaf frames into one, corrupting the conclusion.
- **py-spy's `--format raw` output carries no thread ids or names** — each stack line starts at the process cmdline and the thread-bootstrap frames, nothing more. To scope per-thread you must classify stacks by their thread-entry frame (e.g. `_run_scheduler (...)` for the scheduler thread, `_run_request_builder` for request-build pool workers, the stage service's `_worker (...)` for its worker thread); run `py-spy dump` first to learn which entry frames map to which named threads, then group the raw stacks by those frames.
- **Report the sampling scope separately**: a process-wide "total sample count" doesn't tell you how much of that landed on the scheduler thread you actually care about — verified in this repo that a process-wide `--idle` capture had roughly 89% of leaf frames in thread-pool-wait code (`concurrent.futures.thread`/`threading`/`selectors`), burying the scheduler thread's real signal; narrowing the scope to the scheduler thread itself (identified by its thread-entry frame, e.g. `_run_scheduler` — don't assume it's the "main" thread) surfaced real signal (`from_schedule_batch`, `_sleep_during_idle`, forward-pass frames) that was invisible in the aggregate. Report both a process-wide share and a scheduler-thread-only share as two separate numbers, each with its own stated denominator (the total sample count within that specific scope, not a generic "total samples").
- Take one pass with `--idle` and one without: the `--idle` pass shows the share of time blocked/waiting, while the non-`--idle` (pure on-CPU) pass shows the real CPU-time hotspots. These answer two different questions — don't mix the two datasets when answering "where is it blocked" vs. "where does CPU time actually go."

### Layer 3: Concurrency Sweep — Can Stacking Concurrency/Batch Push Up Utilization?

Standard sweep design: hold everything else fixed, sweep concurrency ∈ {8, 16, 32, 64} (or the model's own `max_running_requests` hard cap), with at least 2–3 repeats per point plus one warmup pass excluded from the stats, while sampling GPU utilization and recording throughput/latency/accuracy (WER or whatever the modality's equivalent metric is). For the utilization sampling, use the benchmark's built-in sampler where the entrypoint has one (e.g. `benchmark_asr_seedtts.py`'s `--sample-util`, see §4 for its two-monitor caveat); for entrypoints without one (e.g. `benchmark_tts_serving.py`), tightly bracket the workload with the external `nvidia-smi`-loop or DCGM sampling already described in Layer 1 methods 2–3 — the sweep design does not depend on any one script's flags.

**If the model has clearly distinct typical workload shapes (e.g. short-clip vs. long-audio for ASR), run the concurrency sweep separately for each shape — don't let one shape's sweep stand in for all of them**: Layer 1 already noted that the busy-ratio trend as a function of concurrency can flip entirely between short-clip and long-sequence workloads (see the decision rule at the end of Layer 1 above); the same shape difference can also change the throughput/latency curve shape and the "optimal concurrency" conclusion that Layer 3 measures — having already covered both shapes in Layer 1 does not mean Layer 3 can get away with testing only one. This repo usually already has separate eval scripts per shape (e.g. `benchmarks/eval/benchmark_asr_seedtts.py` for short clips, `benchmarks/eval/benchmark_asr_longform.py` for long audio) — when both shapes are in scope for the target use case, sweep both rather than just whichever script is at hand; a model that's only meaningfully used in one shape (e.g. one not designed for long sequences at all) can skip the other, but say so explicitly in the report rather than silently testing only one and treating it as complete.

Criterion for a "negative result" (i.e. "stacking concurrency doesn't move utilization"): mean GPU utilization does not rise monotonically with concurrency, and may even be lowest at the hard cap; meanwhile the marginal throughput gain shrinks noticeably and tail latency (p95) clearly worsens. This pattern means the throughput gain comes from amortizing a fixed per-step scheduling cost over a bigger batch, not from GPU compute actually getting busier — pushing concurrency/batch further won't buy more utilization, only worse tail latency.

**Also check**: cross-reference against an `nvidia-smi` snapshot of a *different* GPU (or a different `--gpu-index`) taken during the same load test, to confirm you haven't mistakenly attributed an external tenant's utilization to your own run (this is the same pitfall as the GPU-selection one in §1, just in its "at runtime" form). This pitfall isn't limited to "you didn't check cleanliness carefully enough at selection time" — a GPU confirmed idle at the start of an investigation can pick up a tenant mid-run from a **completely unrelated code checkout/session on the same host** (none of your own processes), and that occupancy may be transient and clear up again on its own rather than meaning the GPU is unusable long-term; when you spot-check during a run and see something unexpected, identify who the occupant actually is before deciding whether to switch GPUs or just annotate the contention window — don't reflexively switch GPUs the moment utilization ticks up.

**Aggregate throughput (`completed / wall_clock`) is extremely sensitive to a single tail-latency outlier — a large sample count does not make you immune**: if the dataset contains even one sample that triggers anomalous model behavior (some edge-case input causing runaway generation far beyond normal length, or getting stuck in a retry/timeout path), that single sample can occupy one concurrency slot for as long as — or longer than — the combined total of every other sample. In that case the run's aggregate throughput gets dominated by this one sample, and a "large" sample count (hundreds) does not average this out, because averaging-out assumes the outlier's effect is bounded additive noise, while a genuine far outlier's latency can be the same order of magnitude as the sum of everything else. **How to check**: if throughput reads unexpectedly low, or drops by an order of magnitude as you scale up the sample count, look first at the **single maximum latency** in that run — not the mean/p50/p90, which may not even show anything unusual when there's only one outlier. Once you've spotted a latency far outside the rest of the distribution, confirm it, then re-run with that sample excluded and check whether throughput recovers to the expected range. Conversely, don't jump straight to "concurrency scaling got worse" or "the dataset is ordered unevenly" as an explanation for "throughput dropped an order of magnitude after growing the sample count from tens to hundreds" — sort the per-sample latencies first; it is often a single specific sample at fault, not a distributional issue.

**Another common pitfall**: on a shared sandbox host, the PID attribution reported by `nvidia-smi --query-compute-apps` can be unreliable (the local process namespace and what `nvidia-smi` observes may not agree, causing your own memory allocation to be misreported as belonging to an "external process"). In a container this is systematic, not occasional: `nvidia-smi` reports host-namespace PIDs, so *every* compute-app row — including your own server's allocation — shows a PID that local `ps` cannot resolve; "PID not found locally" is therefore expected and proves nothing either way. Attribute by bracketing instead: memory that was 0 before your boot, appears at boot, and returns to 0 after your teardown is yours regardless of the reported PID. If you suspect external contention, cross-check by killing your own process and confirming whether the reported occupancy disappears along with it — don't trust the PID-attribution column alone. Note also that the mid-run-tenant pitfall applies to the **cross-check GPU itself**: an idle GPU chosen as the misattribution control can get grabbed by an external tenant mid-run, making the control read high; a nonzero cross-check reading means "identify the occupant via `--query-compute-apps` and switch controls," not "my sampling is misattributing."

**When busy ratio drops (rather than rises) as concurrency increases, and fluctuates a lot rather than trending smoothly**: this pattern is easy to misread as "we just haven't stacked enough concurrency yet," but it can also be a host-bound symptom — CPU-side scheduling/synchronization overhead getting heavier as concurrency rises, opening up more/longer gaps in the GPU kernel timeline and dragging the busy ratio down. That's a different root cause from "GPU compute is genuinely light and stacking concurrency can't raise utilization," and points to a different fix. How to tell them apart: pull a short nsys trace at each of the concurrency points you're comparing (reuse the capture method from Layer 1 method 4 above, with `osrt` included in `--trace`), and check whether the rate of host-side synchronization/wait syscalls (e.g. `pthread_cond_wait`/`pthread_cond_timedwait`) rises noticeably with concurrency, in step with the busy-ratio drop. **This is corroborating evidence, not proof** — a rising wait-syscall rate alongside a falling busy ratio is consistent with heavier host-side sync overhead, but that correlation alone doesn't establish causation. It is, however, enough to justify pivoting the next investigation step toward CPU-side scheduling/sync logic rather than continuing to tune GPU kernels.

### Layer 4: A/B Switch Experiments — Validating a Specific Candidate Optimization

Once Layer 2 has turned up a suspected source of overhead (a default-on switch, a thread-pool size, etc.), design a clean A/B:

1. **Change exactly one variable**, holding everything else — config, GPU, dataset — fixed. Prefer a CLI override over changing a code default, so you can switch quickly.
2. **Warmup policy must be identical across both arms** — running one arm with `--warmup` and the other without introduces confounding noise. The correct approach is to base your headline conclusion only on the two methodologically-matched runs; a mismatched-method run can at best serve as directional supporting evidence. **When each arm restarts the server independently, watch for the "first substantial load is slower than steady state" effect already noted in §1** — the eval script's own warmup pass may not be enough to fully absorb it, and if one arm's headline number happens to come from "right after restart" while the other's comes from "after several passes," you can mistake this effect for the A/B variable's own effect. Make sure both arms have already cleared the cold-start period before recording the numbers you'll use for the headline conclusion (e.g. run one real, substantially-sized pass that isn't counted in the stats first, or confirm the same sample-id batch's numbers converge between a first pass and a repeat).
3. **GPU environment must be identical across both arms** (either both on a clean GPU, or both under the same degree of tenant contention) — if the GPU gets grabbed by an external tenant mid-run and memory is forced to shrink, that run's throughput numbers can't be used for a performance conclusion; but it's still usable if all you're validating is a qualitative question like "did this overhead's sample share drop to zero."
4. **Judging "no functional/accuracy regression"**: check at minimum that (a) the server completes startup stages like weight loading / CUDA graph capture normally, (b) the accuracy metric matches the baseline, and (c) throughput/latency don't visibly get worse. Only once all three pass can you say "turning this off/changing this is safe."
5. Re-run the Layer 2 py-spy sampling as well, to confirm whether the suspected overhead's leaf-frame share has actually dropped to/near zero — don't rely on throughput numbers alone (throughput can wobble from noise, but a leaf-frame share going to zero is more direct causal evidence).
6. **Do 2–3 repeats** (same rationale as Layer 2), so a single-run result doesn't get skewed by sampling noise. **And measure the noise floor before claiming a small effect — don't guess it.** Repeats alone tell you the spread within one protocol, not whether the protocol itself is too noisy for the delta you're claiming. Observed in this repo: a restart-based A/B on a shared host showed a ~9.6% band, and two *identical* baseline servers differed by ~6.5% — while an A/A calibration using alternating interleaved pairs against two live servers brought the local floor down to ~2%. So: for any claimed delta in the single-digit-percent range, first run an A/A (baseline-vs-baseline) calibration under the exact same protocol as your A/B, and only call the effect real if it clearly clears that *measured* band; when host drift is material (shared tenants, long wall-clock), prefer interleaved A/B pairs against live servers over restart-per-arm designs. Paired dual-server runs aren't required for every experiment — but a small delta without an A/A floor is a "medium" finding at best, not "strong".
7. **Before running the A/B at all, work out whether the switch's effect is a deterministic, boot-time-computed configuration outcome rather than runtime behavior.** For example, a switch that turns on "compilation/optimization" may in practice be gated by a separate capacity parameter (some "max batch size this applies to" setting) that caps its real coverage far below the actual serving concurrency (e.g. `max_running_requests`). That kind of capacity cap is typically computed once at startup — deciding which batch buckets keep getting the optimized treatment and which fall back to the plain path — independent of runtime traffic patterns. **In that case, reading the scheduler/graph-capture code's bucket-capacity computation is enough to settle the question; you don't need to actually boot a server and re-measure.** Save the live-measurement effort for questions that are genuinely runtime behavior — dependent on scheduling or traffic patterns — that code-reading alone cannot resolve. Conversely, runtime-behavior questions cannot be settled by code-reading alone — these are different categories of claim, and using the wrong verification method for either (demanding runtime structural evidence for a deterministic config, or trusting code-reading alone for runtime behavior) wastes verification effort either way. **If circumstances make live verification disproportionately costly (e.g. reproducing it would require modifying infrastructure code shared across multiple sessions/tenants, where the risk outweighs the benefit), code-level evidence alone can still be recorded as the finding — but say so explicitly in the writeup ("code-level evidence only, not re-verified at runtime") rather than blurring it into a claim that was empirically measured.**

### Layer 5: Functional Correctness Regression — When You Must Re-Verify Accuracy

The following scenarios **require** a dedicated functional regression pass — don't rely on whatever dataset happened to get exercised as a side effect of Layer 3/4:

- **After changing any default value or scheduling logic**, even if the A/B stage already validated no regression on a short-sequence dataset, also run it on a long-sequence / structurally-different dataset — different input lengths/structures can take entirely different request-chunking code paths (e.g. inputs exceeding a single max length that must be chunked).
- **Any change touching attention-backend / CUDA-graph compatibility** needs special attention to encoder-decoder (as opposed to pure decoder-only) model edge cases. Prefer a structural check ("this is an encoder-decoder model → default to more conservative behavior") over maintaining a per-backend blocklist — a new backend reusing an old backend's implementation without being added to an existing blocklist is exactly the kind of thing that's easy to miss.

## 3. Checklist for Whoever Picks Up the Next Model

When you take on a profiling task for a new model, work through this in order:

1. [ ] Record the baseline environment (framework version, GPU model, model checkpoint, dataset version) — and the profiled repo's own commit SHA plus whether the working tree was dirty (`git rev-parse HEAD`, `git status --short`). A profiling conclusion is only interpretable against a known code state; without the SHA, nobody can later tell whether a finding still applies.
2. [ ] Pick a GPU via `nvidia-smi --query-gpu=...` that's both low-utilization and has enough free memory, and keep watching for mid-run preemption throughout.
3. [ ] Layer 1: run either the kernel-timing or the nvidia-smi sampling method once, to decide whether the bottleneck is GPU compute or CPU/orchestration. If there's already an existing concurrency/bottleneck doc for this model, read it first to avoid reinventing the wheel — you can build directly on top of it and just fill in whichever layers are missing.
4. [ ] If the bottleneck is CPU/orchestration: do the Layer 2 py-spy sampling (remember `--idle`), pin down the highest-share leaf frame, and do 3 repeats to confirm it isn't noise.
5. [ ] Layer 3: run the concurrency sweep to confirm whether "stacking concurrency" moves utilization, and keep a table of GPU util vs. concurrency; if the model has distinct short-form and long-form workload shapes, sweep both — don't draw a conclusion from just one.
6. [ ] For each suspected overhead source found in Layer 2, design a clean Layer 4 A/B (one variable at a time, warmup/GPU environment matched across arms), and only draw a conclusion once functional/accuracy regression is ruled out.
7. [ ] Layer 5: run a functional regression on at least one long-sequence / structurally-different dataset — don't trust results from a short-sequence dataset alone.
8. [ ] Write up the report, structured by layer: what method was used, what was found, and the strength of the evidence — negative results should be stated clearly too, e.g. "ruled out, no change needed" — plus a finding-evidence-recommendation table. Grade evidence strength against this rubric, not by feel, so gradings are comparable across runs and across people:
   - **strong** — ≥3 repeats converging, or a one-variable A/B with matched warmup/GPU environment, and the effect is clearly above the *measured* run-to-run noise (for small deltas, established via an A/A calibration — see Layer 4 item 6, not guessed);
   - **medium** — a single clean run with a clear direction, not yet repeated or A/B-confirmed;
   - **weak** — indirect inference, or a run with a known confound (shared-host contention, sampling-window bias, unconverged warmup).

   Every number in the report must be traceable: record the exact command that produced it and the path of the raw artifact it came from (py-spy output, benchmark log), saved alongside the report — a number nobody can trace back to a command is a claim, not evidence.
9. [ ] Any general-purpose pitfall you hit along the way that isn't specific to your model (a new py-spy gotcha, a new GPU-contention pattern) should be folded back into §1/§2 of this document, so the next person doesn't have to rediscover it.

## 4. General Tools / Scripts Index

**Check the script's own `--help` first to see whether it attaches to an existing server or manages its own**: different eval scripts vary in how they support this — some default to owning the server's lifecycle, others need an explicit flag like `--use-existing-server` before they'll attach to a server you started manually. If you started a server by hand and ran the script without checking this, the common failure mode is the script trying to launch a second server on the same port and immediately erroring out on a port conflict. Profiling/A-B scenarios generally need you to control the server lifecycle manually (e.g. sharing one launch across two configs, or inserting a py-spy capture in between), so confirm the script supports attach mode before proceeding.

- **py-spy sampling**: `py-spy record --format raw --idle --subprocesses --pid <pid> --duration <s> --rate 20` (start at `--rate 5` on an unfamiliar target and watch for lag — see Layer 2); to peek at a live thread stack, use `py-spy dump --pid <pid>`.
- **CPU pinning/isolation**: `.github/scripts/pin_to_ci_cpuset.sh`, `_apply_omni_ci_cpuset`/`_parse_cpuset` in `tests/test_model/conftest.py` (`os.sched_setaffinity`), `examples/mps_dp/{launch,autodp}.sh` (`numactl --cpunodebind/--membind/-C`) — reuse these on a shared host instead of inventing a new pinning scheme.
- **GPU utilization / selection check**: `nvidia-smi --query-gpu=index,utilization.gpu,memory.used,memory.total --format=csv`.
- **Short-clip concurrency/accuracy eval**: `benchmarks/eval/benchmark_asr_seedtts.py` (`--sample-util --util-gpu-ids <gpu>` samples GPU utilization — note this script has **two independent GPU monitors**: the always-on resource monitor (`--gpu-index`, defaults to GPU 0) writes the per-repeat `resources` block, while `--sample-util --util-gpu-ids` writes the separate `utilization` block; if your server isn't on GPU 0 and you only set `--util-gpu-ids`, the `resources.gpu_util_percent` field will read ~0 for the wrong GPU — read the `utilization` block, or point `--gpu-index` at your GPU too. Also note the built-in sampler persists only per-repeat min/mean/max summaries, not the raw sample series — if you need the raw ramp/plateau curve, bracket the run with your own sampler loop per Layer 1 method 2; `--profile-events --profile-event-dir <dir>` captures a per-request stage breakdown, `--fingerprint` records an environment fingerprint, `--save-raw-dir <dir>` saves the raw per-request JSONL). **Scope of the request-level stage profiler**: it actually produces two independent breakdowns — the intra-stage phase intervals (queue-build, queue-wait, prefill, decode) and the inter-stage hop-switch latency. Models with only one stage (all ASR-family models today) have no "hop" to speak of, so that half is empty for them; but the phase-interval breakdown is still meaningful for single-stage models (it isn't "sliced for nothing") — GPU-side DCGM/nsys metrics measure GPU occupancy and don't substitute for this CPU-side request-lifecycle phase breakdown. The hop breakdown is only useful for multi-stage models (TTS/omni, e.g. LM decode + vocoder).
- **Long-audio concurrency/accuracy eval**: `benchmarks/eval/benchmark_asr_longform.py` (reuses `benchmark_asr_seedtts`'s `_sweep`/`_evaluation_input_sha256`/`_print_table` infrastructure), with a companion dataset-prep script at `benchmarks/dataset/prepare.py --dataset <longlibriheavy-30|longlibriheavy-60|meanwhile>`.
- **CUDA kernel-level profiling**: the native `/start_profile` (HTTP endpoint) + `/stop_profile`, exporting a chrome trace (`sglang_omni/profiler/torch_profiler.py`) — you'll need to write your own script to parse the `cat=="kernel"` groups, since there's no built-in summary table.
- **DCGM continuous sampling (SM/Tensor Active)**: `dcgmi dmon -e 1002,1004 -d <sampling interval ms> -i <gpu-index>` (`1002`=SM Active, `1004`=Tensor Active, requires `nv-hostengine` resident). See Layer 1 method 3 for details — prefer this over nsys for day-to-day/long-running scenarios; it's lighter weight.
- **nsys GPU Metrics (SM/Tensor Active, one-off deep-dive)**: `nsys profile --trace=cuda,osrt,nvtx --gpu-metrics-devices=cuda-visible --gpu-metrics-set=<check with --gpu-metrics-set=help> --gpu-metrics-frequency=100 -o <out> -- <full launch command>` (must wrap the whole launch — don't attach after the fact), then `nsys export --type sqlite -o <out>.sqlite <out>.nsys-rep` and read the `GPU_METRICS` table. See Layer 1 method 4 for details.
